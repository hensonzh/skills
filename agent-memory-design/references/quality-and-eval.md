# Quality and Evaluation

记忆系统的质量是个长期问题。写得多不一定好，读得多不一定准。需要从写、读、运行、用户体验四个维度持续测量。

## 1. 写质量指标

- **抽取准确率（precision）**：抽取候选中真正应该写入的比例。
- **抽取召回率（recall）**：应该被抽取的信号被抽取的比例。
- **冲突率**：同 key 多次出现导致冲突的频率，过高说明 schema 设计或抽取规则不稳。
- **覆盖率**：用户表达的 key 被抽取的覆盖率（按 fact / preference 分别统计，episodic 不强求）。
- **type 错配率**：把 derived 写成 fact 的比例，必须 < 1%。
- **黑名单触达率**：抽到了高敏类目并被拒绝的次数（健康监控用）。
- **抽取失败率**：抽取 job 异常退出 / schema 校验失败 / 触发限流的比例。
- **每 run 抽取量分布**：长尾过高时多半是抽取过度。

## 2. 读质量指标

- **召回 hit rate**：query 拉到至少一条相关记忆的比例。
- **注入相关性**：被注入的 snippet 与本轮回复的相关性（LLM-as-judge 或人工评分）。
- **注入污染率**：模型在没有依据时引用某条记忆，或编造 memory 引用。
- **token 浪费比**：注入 token 中未被回复实际使用的比例。
- **错误注入危害**：fact 错误导致回复事实错误的次数（最严重的指标，必须接告警）。
- **裁剪损失率**：因 token 预算被裁掉的 snippet 中有多少其实是相关的。
- **derived 被当 fact 引用率**：通过 LLM-as-judge 判断模型是否把推断输出为确定事实。

## 3. 评估方法

### 标注集（gold set）

- 至少 200~500 条对话片段 + 期望 memory 输出。
- 覆盖正例、负例、边界场景：
  - 显式偏好。
  - 隐含但应抽取。
  - 隐含但不该抽取（如假设、情绪）。
  - 需要冲突解决。
  - 需要 supersede。
  - 高敏类目（应被拒绝）。
- 每半年滚动更新，淘汰失效用例并补新场景。

### LLM-as-judge

- 用更强模型判断抽取候选是否合规、注入是否合理。
- 必须固定 prompt 模板和评分 rubric，单条结果带分数 + 简短解释。
- 用作粗筛与回归监控；不替代真人标注。
- 周期跑：抽取候选随机抽样、注入回放随机抽样。

### 用户反馈

- 在记忆管理 UI 给"这条不对 / 这条有用 / 不该记这个"按钮。
- 反馈直接关联 `memory_id` 与 `turn_id`，写入 audit log。
- 反馈用途：删除 / 降权 / 微调抽取 prompt 与权重。

### A/B 实验

- 排序权重、token 预算、注入格式、抽取 prompt 任何变更必须 A/B。
- 指标：用户满意度、回复修改率、跟随对话长度、转化（业务相关）。
- 注意 A/B 的"上下文公平"：不能两组用户看到完全不同的记忆条目，应固定记忆库、变化策略。

### 离线回放

- 保存 retrieval query + injection block + 模型输出三元组，便于策略变更后回放。
- dry-run 模式：策略修改后不写日志、不影响线上，仅生成对比报告。

## 4. 运行时监控

实时指标（建议接 dashboard）：

- 写入速率 / 拒绝率 / 错误率（按 type、scope、原因分组）。
- 各 type 的活跃量（active vs superseded vs deleted）。
- 平均 retrieval 延迟（P50 / P95 / P99）。
- 平均注入 token / 注入命中率 / 裁剪率。
- 删除请求量（区分用户主动 vs 合规请求）。
- 隐私事件：黑名单触达、跨 scope 访问尝试。
- 冲突事件：冲突解决方式分布。
- TTL 清理量。

告警建议：

- type 错配率突增 → 立即查抽取 prompt 与 validator。
- 高敏类目写入尝试连续多次 → 安全告警。
- retrieval 失败率突增 → 检查向量索引、storage 健康。
- 跨 scope 访问尝试 → 严重，自动暂停相关 endpoint。
- 单用户记忆条数突破上限 → 检查抽取过度。

## 5. 回归测试套件

每次发布或抽取/检索/排序变更必跑：

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| W1 | 用户 explicit 偏好 | 写入 preference；下次新会话被读出并注入 |
| W2 | 用户更正旧偏好 | 旧 preference status=superseded；新值生效 |
| W3 | 模型推断 derived | 写入 derived 且带 evidence；低置信不进 prompt |
| W4 | 高敏类目抽取（健康） | validator 拒绝；audit log 记录；不进 prompt |
| W5 | 假设性表达 ("如果我去 X") | 不抽取 |
| W6 | 当下情绪 ("好累") | 不抽取 |
| W7 | 同 key 不同 value | 按既定冲突策略解决；version 单调递增 |
| R1 | 用户软删除某条 | retrieval 不再返回；audit 保留 |
| R2 | 用户硬删除全部 | 物理删除；向量索引清理；管理面板可见 |
| R3 | TTL 过期 | episodic / derived 同规则：状态置 superseded 或物理删除（按合规策略），retrieval 不再返回 |
| R4 | 注入 token 预算超限 | 按优先级裁剪，核心低敏 fact 优先保留；裁剪进日志 |
| R5 | 跨 scope 访问 | 拒绝并日志记录 |
| R6 | 模型在没有相关记忆时回答 | 不引用任何 memory snippet（注入污染率监控） |
| R7 | retrieval miss | 返回空，模型继续回答不假装 |
| R8 | derived 与 fact 冲突 | fact 优先，derived 标 outdated |
| R9 | 大体量用户 (≥ 500 条) | retrieval 在预算内仍能拿到关键 fact |
| R10 | 同时多端写入同 key | 按 conflict 策略解决 |

## 6. 反指标（vanity metrics）

不要把这些当核心 KPI：

- **写入总条数**：写得多不等于有用，可能是抽取过度。
- **整体注入命中率**：不区分 fact 与 episodic 的命中率会误导，fact 必然 100%，episodic 才反映系统价值。
- **用户"喜欢" rate**：没有对照组就没有意义。
- **召回率**：召回高但 precision 低反而更糟。
- **平均记忆条数**：不能代表"记得对、记得有用"。

真正反映系统价值的：

- 用户接受率（编辑/删除频次的反向）。
- 注入有效率（注入了且回复采信了）。
- 错误注入危害事件数。
- 用户对 agent 的"懂我"主观评分（搭配 A/B 对照才有意义）。

## 7. 评估节奏建议

- 每天：运行时监控 dashboard。
- 每周：随机抽样 LLM-as-judge 报告、用户反馈 review。
- 每次发布：回归测试 + LLM-as-judge 大样本对比。
- 每季度：gold set 更新；策略权重 review；隐私 / 合规检查。
- 每年：全量数据治理（删除超期 audit、重摘要超长 episodic、重新评估 schema）。
