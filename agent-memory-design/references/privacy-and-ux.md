# Privacy and UX

记忆 = 用户授权后由 agent 持有的私人知识。任何越界都会导致信任崩塌，且常带来合规风险。

## 1. 授权模型

授权与写入是**两个独立维度**，不要混用：

- **类目开关（本节）**：用户授权 agent 写哪些 type；关掉后该 type 完全不抽取、不写入。
- **写入门槛（§2）**：在类目已开的前提下，抽取层根据信号强度、置信度、敏感度决定具体是否落库。

三档授权：

| 档位 | 适用 | UX |
| --- | --- | --- |
| **Opt-in（默认关）** | 高敏 / 监管严 / B2B | 用户主动开 |
| **Opt-out（默认开）** | 个人助手 / 学习 / 创作 | 用户可关 |
| **Per-category** | 体量大、类目多 | 按 fact / preference / episodic / derived 单独开关 |

推荐组合：

- 主开关按产品风险选择：普通个人助手可 opt-out；B2B、高敏或监管严格产品用 opt-in。
- 类目细控：fact / preference 可默认开；episodic 默认开但可关；derived 默认关，除非产品明确说明“会学习你的长期模式”并获得授权。
- 高敏类目（健康、财务、未成年人等）固定 opt-in，需要走单独同意流程。

## 2. 默认值建议

下面规则**只在该类目开关已开的前提下生效**；类目关闭时全部跳过抽取。

- **fact 写入门槛**：显式声明的写；从行为推断的不写。
- **preference 写入门槛**：显式声明的写；行为推断需达到产品设定的证据门槛，且 derived 已获授权，再由用户确认是否转为 preference。
- **episodic 类目开关**：按产品用途与授权设置；保留期限按需要确定，90 天可作评估起点。
- **derived 类目开关**：通用默认关；仅在学习/coach/长期陪伴类产品明确说明并获得用户授权后开启。

新用户首次进入产品时，建议提供：

- 一段简短的"agent 会记得什么"说明（≤ 80 字）。
- 一个查看/编辑/关闭入口。
- 不要在第一次回复里炫耀"我刚刚记住了……"。

## 3. 可见性 / 管理 UI

至少暴露：

- 全部记忆条目（按 type 分组）。
- 每条字段：key、value、type、来源（kind + 简短描述）、创建时间、最近读取时间、置信度（如适用）。
- 操作：编辑、删除、停止学习这一类、举报"这条不对"。
- 一键导出（JSON）/ 一键清空（强二次确认）。
- 类目级开关。

不要：

- 默认展示 evidence 原文。提供"展开来源"按钮，点了再显示。
- 把 audit log 直接展示给用户；提供"我对这条做过什么"的精简视图。
- 在 UI 里暴露内部 id（mem_xxx）；用语义化标签。

## 4. 编辑与删除

### 编辑

- 用户改 fact / preference → 写新版本，旧版本 `status=superseded`，audit 记录变更前后。
- 用户**不应**直接编辑 episodic / derived 内部字段；提供"删除并重学"或"举报不准"。
- 编辑后下一次 retrieval 必须读到新值；不允许缓存旧值。

### 删除

- **软删除**：`status=deleted`，UI 不再展示，retrieval 不再返回。提供撤销窗口（如 7 天）。
- **硬删除**：清理主表、向量索引、缓存和相关副本；audit 按既定保留规则处理，仅保留必要 metadata。
- **触发场景**：用户主动 / 用户清空 / 合规要求（GDPR、CCPA、个保法）。
- 单条删除已有明确对象和授权时可直接执行并反馈；批量或影响不明确的删除先说明范围并确认。
- “忘掉刚才那句”先定位对应信息，覆盖相关 fact、preference、episodic、derived 及其副本；指代不清时再澄清。

### 反例

- 删除按钮只删 UI，不删后端 → 信任崩塌。
- 删除后 audit 仍保留完整 evidence 与 value → 合规漏洞。
- 不区分软/硬删除，用户分不清。
- 把"暂停记忆"和"删除记忆"做成同一个开关。

## 5. 合规接触点

主要法域常见要求与对应能力：

| 要求 | 对应能力 |
| --- | --- |
| 数据访问（查看自己有哪些记忆） | 管理面板 + 导出 |
| 数据可携（machine-readable export） | 一键导出 JSON 格式 |
| 数据更正 | 用户编辑 + audit |
| 数据删除（被遗忘权） | 硬删除 + 索引清理 + audit metadata |
| 数据驻留 | 跨境前评估；按区域部署或加密 |
| 同意撤回 | 关闭主开关 / 类目开关；停止后续抽取 |
| 审计 | 完整 audit log（写、读、删、共享） |
| 未成年人 | 单独同意流程；不写敏感推断 |
| 高敏类目（健康/财务/法律） | 与平台合规共审；默认不写 |

实施建议：

- 把"用户的记忆数据"作为一类一等数据资产管理，不要散落在多个微服务。
- 删除走统一 pipeline（user delete request → 主表 + 向量 + 缓存 + 备份），避免遗漏。
- audit log 设独立访问权限；不允许应用层任意写入。

## 6. 跨设备与同步冲突

- 记忆按 `user_id`/`scope_id` 同步，不绑定设备。
- 多端修改同 key 按声明的类型策略合并；fact 仍需显式更正或确认，不能仅凭 `updated_at` 覆盖。其他类型可采用时间优先，并保证版本单调递增。
- 离线变更上线时按 version 合并；冲突无法解决时给用户提示并保留两份等待选择。
- 长时间不上线的设备同步前应做 schema 兼容性校验。

## 7. 多用户与共享

| 场景 | scope | 设计要点 |
| --- | --- | --- |
| 单用户个人助手 | `user` | 默认隔离，无共享 |
| 家庭 / 团队助手 | `team` | 显式标记 owner、admin、member；写权限可配 |
| 协作 agent | `team` + `team_shared=true` | 共享必须显式开；默认不分享 |
| 切换"代理人格"或角色 | 切换/重置 scope | 避免"医生模式"看到"朋友模式"的记忆 |

约束：

- 共享 scope 不应自动包含敏感类目；高敏字段必须额外开关。
- 写入者标识在共享 scope 中默认匿名化；只在 audit 中保留真实 actor。
- 用户离开团队 / 退出共享时，团队 scope 中由该用户写入的条目按规则处理（保留 / 标匿名 / 删除）。

## 8. 安全边界

绝对不存（除非产品定位明确且合规审批）：

- 密码、token、API key、二维码秘钥。
- 身份证号、护照号、银行卡号、信用卡 CVV。
- 健康诊断、就诊记录、用药记录。
- 性取向、宗教、政治观点。
- 未成年人敏感信息（具体住址、学校、时间表）。

注入与读取保护：

- 注入前必须做：PII 最小化、scope filter 强制、高敏类目过滤。
- 模型不应能直接看到其它用户的记忆；即使 share scope 允许，也通过受限 read tool。
- 对 prompt 注入攻击（如用户故意诱导写敏感推断）要有抽取层 deny rule + LLM-as-judge 监控。
- 任何记忆相关接口默认带 rate limit，避免被恶意刷库。

## 9. UX 反例

- 没有任何 UI 让用户看到 agent 记住了什么。
- 删除按钮只删 UI，不删底层。
- "Remember me"一个总开关，什么都开 / 什么都关。
- 在每次回复里都列出"我刚才更新了什么记忆"——体验噪音；放管理面板的通知中心。
- 用户改 fact 后下一轮回复仍引用旧值（缓存没失效）。
- 关闭记忆主开关后 agent 仍声称"还记得你说过……"。
- 让用户面对一长串内部 key（`derived.weak_topic.xxx`）。
- 把高敏类目（健康/财务）放在普通类目开关中，让用户在不知情下打开。

## 10. UX 正面模式

- "你来过两次，agent 记得 X 与 Y"，给用户控制感而不是惊讶感。
- 关键节点（如更正 fact、写入新 preference）有轻量回执。
- 管理面板支持"按主题"过滤而不是按内部 type。
- 首次写入敏感类目前显式弹出确认与说明。
- 清空全部记忆等重大变更说明范围并确认；产品需要更强防误触时再使用输入确认词。
- 提供"暂停记忆 N 天"开关，给用户低成本"安静"模式，不必清空。
