# 示例：客服查询与退款

本例复用项目已有的消息存储、运行检查点和业务 API。退款按该产品规则需要确认；已获自动执行授权的其他产品不照搬这一步。

## 职责选择

| 数据 | 所属职责 |
| --- | --- |
| 客服行为与授权规则 | 可信指令 |
| 本轮问题、时间与附件引用 | 当前调用输入 |
| 消息与必要工具结果 | 历史组装 |
| 订单和政策 | 有权限校验的业务读取工具 |
| 回答语言 | 记忆服务返回的最小投影 |
| 退款参数、授权与执行结果 | 业务动作记录 |
| 进度与退款预览 | 前端状态与产物 |

这些职责不要求独立数据库。字段形状参考 [schemas.md](schemas.md)，状态与压缩以 [context-management-reference.md](context-management-reference.md) 为准。

## 查询

```text
用户问题 -> 读取运行状态 -> 组装必要上下文
  -> 按权限读取订单/政策 -> 返回模型所需字段和用户可见摘要
  -> 模型回答 -> 记录历史与必要检查点
```

政策引用保留版本；只有内容仍可见且有效时才复用。压缩后需要原始条款，或问题和版本变化时重新读取。资料中出现“忽略规则”等文字仍属于资料，不改变客服权限。

## 退款与结果不明

```text
用户请求 -> 读取订单与政策 -> 确定退款参数
  -> 保存动作及预览 -> 等待确认
  -> 校验确认对象、版本、权限和有效期
  -> 使用持久化的同一幂等键调用退款接口
  -> 成功回执：记录 applied，返回结果
  -> 响应丢失：记录 unknown，查询下游状态后再决定是否重试
```

检查点保存恢复位置，业务记录保存退款状态；二者不能互相替代。用户刷新时从这些记录恢复预览或实际结果，不从聊天里寻找“已退款”字样。

## 受影响路径的验证

| 场景 | 预期 |
| --- | --- |
| 相同工具结果同时来自历史和本轮输入 | 组装时去重，调用与结果仍配对 |
| 压缩后仅有政策 ID | 需要细节时可重新读取，不假定全文仍可见 |
| 用户更改退款参数 | 原授权覆盖范围重新校验，不能盲用旧确认 |
| 执行前崩溃后恢复 | 从记录重建同一操作与幂等键 |
| 下游已退款但回执丢失 | 查询到成功后同步状态，不重复退款 |
| 两端同时确认 | 按业务去重与并发约束只执行同一操作一次 |
| 用户关闭或删除语言记忆 | 以后有效投影不返回旧值；历史可见内容按产品约定处理 |
| 第三方政策含恶意指令 | 保留数据身份，不扩大工具授权 |

示例验证需接实际实现运行；文档中的期望不等于测试结果。
