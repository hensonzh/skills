# 需要核实的架构决策

先从现有代码、产品约定和框架配置取证；只追问会改变本次方案的缺口，不按清单逐项询问。

| 决策 | 需要知道什么 |
| --- | --- |
| 任务范围 | 单轮、多轮还是长任务；有哪些入口和可观察的完成条件 |
| 历史与状态 | 谁负责消息组装，运行状态在哪里，能否恢复与并发更新 |
| 数据与权限 | 哪些事实来自业务系统、用户或第三方；授权主体和新鲜度要求 |
| 长期记忆 | 是否真的跨会话复用；本次只要投影还是要完整记忆设计 |
| 工具与副作用 | 既有授权、重试边界、幂等支持、结果不明时如何查询 |
| 产物与前端 | 哪些数据给模型、哪些给用户；是否需要持久化和后续编辑 |
| 预算与压缩 | 窗口和输出余量、延迟、历史增长、压缩后的重读需求 |
| 隐私与保留 | 适用的数据限制和产品承诺；未知时不默认“无要求” |

无法获得信息时，只对可逆实现选择提出明确假设；权限、敏感数据和不可逆操作不能靠假设补齐。不要默认项目具有托管历史、向量库或固定确认流程。

现有项目优先查看请求组装、历史来源、检索工具、检查点和授权记录。局部审查只报告相关问题；需要完整方案时再说明数据流、决策依据与验证，不要求固定报告章节。
