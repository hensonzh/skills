# Agent 上下文需求发现清单

这份清单用于 0→1 设计智能体上下文模块前的需求收集。回答完这份清单，就能给出有取舍依据的分层方案，而不是凭直觉堆 prompt。

使用方式：

- 设计前先走完 A–I 九组问题；改造现有项目时再补 J 组。
- 对每组先问“必问”，不确定时再问“可选”。
- 信息确实拿不到时，使用“MVP 默认假设”，并把假设记入设计文档，作为后续校验点。
- 不要机械地向用户抛完整问卷。能从代码、产品描述或已有文档读到的，先读；只追问会改变架构决策的缺口。
- “MVP 默认假设”不是最终建议，只是在缺少信息时用于继续推进的保守占位。

## A. 任务形态

必问：

- agent 主要解决哪一类任务？（单轮问答 / 多轮对话 / 长任务 / agent loop / 多 agent 协作）
- 用户从哪些入口触发？是否每个入口的目标和上下文都不同？
- 是否需要在没有用户消息时也工作？（后台事件、定时任务、外部回调）

可选：

- 是否存在子任务嵌套或工作流分支？
- 单个任务最长可能持续多少分钟或多少轮？

MVP 默认假设：

- 单 agent，多轮对话，仅由用户消息触发，单一入口。

## B. 多轮与历史

必问：

- 是否需要多轮上下文？为什么？
- 历史的真实价值是什么？是连续叙事、累计事实、还是仅最近几轮？
- 历史长度的预期上限：典型 / P95 / 最坏？
- history 由谁承接：模型平台 thread/response chain、应用侧消息表，还是混合？
- 哪些事实不能只靠历史复用，必须在需要时重新读取？

可选：

- 是否允许用户编辑或删除历史消息？
- 历史是否需要审计、导出或法律留存？

MVP 默认假设：

- 平台 history 承接连续推理；应用侧至少保存 thread/run 元数据、history pointer、关键 action/artifact 引用和必要审计摘要。

## C. 用户与租户

必问：

- 用户是匿名、登录、还是租户内用户？
- 是否多租户？数据隔离粒度（用户 / 团队 / 组织）？
- 一个用户在多设备上是否需要看到一致的上下文？

可选：

- 是否允许跨用户共享上下文？（家庭、班级、协同）

MVP 默认假设：

- 单用户登录态，按 user_id 隔离 session 与 memory。

## D. 长期记忆

必问：

- agent 是否需要跨会话记住任何东西？
- 哪些事实是“稳定且复用价值高”的？哪些只是“当下相关”？
- 写入路径是用户主动声明，还是模型根据对话推断？
- 用户能否查看、修改、删除自己的 memory？
- 本设计只需要 memory projection，还是需要完整长期记忆系统？如果是后者，本方案只保留上下文边界，完整记忆系统另行设计。

可选：

- 是否需要记忆冲突解决（旧值 vs 新值）？
- 是否对 memory 设过期时间？

MVP 默认假设：

- 不上线模型推断型 long-term memory；仅通过 settings 或用户明确指令保存少量偏好。

## E. RAG 与外部知识

必问：

- 是否需要外部知识？来源：内部文档、产品手册、知识库、代码、第三方 API 还是数据库？
- 数据规模：条目数、单条大小、总体量？
- 更新频率：实时、每天、季度？
- 是否需要按权限或租户分片？

可选：

- 是否需要引用来源（citation）？
- 是否需要混合检索（向量 + 关键词 + 元数据过滤）？

MVP 默认假设：

- 没有 RAG；用 read tool 直接从结构化数据库获取事实。

## F. 工具与副作用

必问：

- agent 需要哪些读工具？哪些写工具？
- 写工具是否会触发外部副作用（扣款、发邮件、改业务记录）？
- 哪些写操作必须用户先确认？
- 是否需要幂等键、重试、取消、超时？

可选：

- 工具是否调用第三方系统，是否有限流和熔断要求？
- 是否需要 dry-run 或 preview 模式？

MVP 默认假设：

- 仅暴露读工具；任何写工具默认走 preview→confirmation→apply 三段式。

## G. 前端、Artifact 与流式

必问：

- 用户是否需要看到中间过程（思考、检索、工具执行）？
- 是否需要结构化 artifact（卡片、表单、报告、计划表）？
- 是否需要流式输出文本？
- 模型上下文与前端展示是否需要不同 payload？
- artifact 是否只是展示结果，还是会被后续 turn 引用、编辑、确认或提交？

可选：

- artifact 是否需要版本与可编辑历史？
- 前端是否需要回填 artifact 数据再发回模型？
- 是否需要独立设计 work panel / stream event contract？如果是，本方案只保留上下文和 payload 边界，完整前端体验另行设计。

MVP 默认假设：

- 文本流式 + 简单进度状态；无可持久 artifact；前端只回填用户明确提交的结构化 inputs。

## H. 合规、隐私与安全

必问：

- 数据中是否包含 PII、医疗、金融或未成年人数据？
- 是否受 GDPR、CCPA、HIPAA、个保法等约束？
- 是否要求“可被遗忘”、数据删除、可导出？
- 哪些字段绝对不能进入模型？哪些不能进前端？

可选：

- 是否需要审计日志（谁访问了什么上下文）？
- 是否需要区域化部署或数据驻留？

MVP 默认假设：

- 无强合规要求；按最小化原则不把原始 PII 进入 prompt 和前端事件。

## I. 性能、成本、SLA 与平台

必问：

- 每轮 token 预算（输入 / 输出）？
- 平均响应时延目标？P95？
- 月调用量级与成本上限？
- 选定模型平台是否提供 prompt cache、managed thread、tool calling、streaming？是否会迁移？

可选：

- 是否多模型混用（强模型主推理 + 小模型摘要 / 路由）？
- 是否做离线评测和回归？

MVP 默认假设：

- 单一模型平台，启用 prompt cache 与 managed history；月调用量做粗估，不预先优化。

## J. 现有实现审查（改造项目时补充）

必看：

- 模型请求在哪里构造？stable instructions、per-turn input、history、tool result 分别在哪里拼装？
- 是否每轮重复注入用户 profile、全量历史、全量 RAG 文档或完整工具 JSON？
- session/run state 存在哪里？是否有过期、并发控制和刷新恢复路径？
- tool registry 如何区分 read / validate / preview / apply？写操作是否有 action_id、确认态和 idempotency_key？
- artifact 是否有独立 store 和 schema version，还是从 assistant 文本里解析？
- 前端 stream 消费的是 provider 原始事件，还是应用侧稳定事件？
- 哪些测试覆盖长对话截断、刷新、重复提交、权限失败和上下文泄露？

可选：

- prompt cache 命中率、平均输入 tokens、工具失败率、action 漏斗是否已有监控？
- 是否存在多模型、多入口、多租户带来的上下文分叉？

审查输出默认格式：

- Findings：严重程度、位置、问题、影响、建议。
- Target Context Contract：目标分层、schema、数据流。
- Migration Plan：最小改动步骤、回归测试、观测指标。

## 输出：Discovery Brief 模板

走完 A-I（改造现有项目时再补 J）后，把答案整理成一份简短 brief，作为后续设计的输入。

```markdown
# Agent Context Discovery Brief

## Agent 概述
- 名称 / 定位：
- 用户：
- 主要场景：

## 关键决策
- 任务形态：
- 历史承接方式：
- 长期记忆：是 / 否，写入策略：
- RAG：是 / 否，规模与更新：
- 工具：读 [ ]，写 [ ]，确认策略：
- 前端 / Artifact：
- 合规要求：
- 性能 / 成本约束：
- 模型与平台：
- 现有实现入口（改造项目时）：

## 默认假设
- 列出本次发现中使用的默认假设（用 MVP 默认开始时尤其重要）

## 风险与悬而未决
- 还需要确认的内容
```

完成 brief 后，再进入分层设计、schema 定义、数据流和测试规划。
