# 个人工作偏好

## 需求确认

- 新任务先用用户的语言简短重述结果、范围和关键限制，询问确认；确认前不调查、修改或执行外部操作。
- 用户回复“确认”“是的”或选择已提出方案后执行；沉默不算确认。
- 已确认范围内持续完成检查与交付；换轮次、恢复会话、补充信息或询问进度不重复确认，只有目标或范围实质变化才重新确认。
- 确认提问保持简短；需要解释时说明这是用户偏好并链接本文件。

## Git 交付

- 在 Git 仓库完成一轮代码或 Skill 修改并通过相关检查后，默认提交本次任务改动，抓取并合并当前分支的远程跟踪分支，再普通推送到该远程分支；无需另问是否提交或推送。明确请求 Git 同步时也适用。
- 操作前检查分支、跟踪关系、工作区和未推送提交；缺少跟踪分支或目标不明时询问，不猜测远程或分支。
- 只暂存本次任务改动，保留已有提交和无关的未提交改动；无关改动阻碍合并时先保护并在同步后恢复，恢复产生冲突同样先确认。
- 遇到任何冲突，说明冲突内容和建议解决方案，等待用户确认后再解决、完成合并、检查并推送；不沿用旧的仓库自动选边例外。
- 无冲突且相关检查通过后推送；远端已最新但本地有待推送提交时也推送。检查失败则修复任务范围内问题，无法解决时报告并停止推送。
- 远端更新导致推送被拒绝时，重新抓取并按上述流程合并；再次因此被拒绝则停止并报告。不强推、不丢弃或覆盖用户改动。
- 完成后简报提交、同步结果及未完成事项。

用户当次明确要求优先，包括跳过确认、仅本地修改、不提交或不推送。长期偏好变更更新本 Skill；项目技术和交付规则由项目或专用 Skill 维护，不复制本文件到项目。
